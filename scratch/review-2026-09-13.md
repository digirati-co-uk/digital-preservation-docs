# Review of the documentation port

2026-09-13. A judgement review of the completed site, the findings, and the three pages that needed
the most judgement: Authentication, METS editability, and the Storage API "where it differs" page.
Grounded in the files as they stand, not in the session's account of them.

## What holds up

The site is in good shape, and better than its own findings files make it sound. The METS section is
an exact port with nothing lost and three deliberate corrections. The editability page handles a
half-built feature the right way - three separate places say what is agreed direction and what the
platform does today, and the judge is named as "not yet part of the platform" with the PR linked.
The Storage API overview does exactly what "where it differs" was meant to do: a row per Preservation
API concept, and an early warning that most readers should not be here at all. The IIIF framing is
honest about being experimental. The quickstart's two tabs are the right split, and the fact that the
own-METS tab is *simpler* than the managed one (four requests, no ETag) is a point in the design's
favour that the page makes without labouring it.

## Errors found and fixed in this review

Six. Two of them are more worrying than the errors themselves.

1. **`editing-mets.mdx` still said the METS is untouched after a pipeline run.** The pipeline finding
   (a run adds everything under `objects/` itself) was applied to three pages, but this one had been
   verified *before* the finding existed, so it kept the original two-reasons paragraph - including
   the sentence "even in the second, where the Preservation API ran the tools, you might not want all
   the files", which is exactly backwards: the pipeline adds them all regardless. Rewritten to keep
   Tom's prose for the external-tools case, which is where it is true.

2. **Two corrections the verification summary records as made were never applied.**
   `findings-V-verification.md` lists finding 14 ("the Storage API is not wholly innocent of METS")
   and finding 16 (the Storage API reads Fedora's database directly) under "corrected in the prose".
   Neither edit existed. `components.mdx` still said "a METS file is just another Binary" and
   `storage-api/overview.mdx` still said "no concept of METS" in two places. Both fixed now. The
   lesson is the important part: **a findings file that says "fixed" is a claim, and it needs
   checking like any other.** The verification agents were good at finding errors and were not asked
   to confirm the fixes landed; nobody diffed the summary against the pages.

3. **"Allow-list" was describing the intended mechanism, not the current one.** The Authentication
   page used the word ten times, and once said the known-clients map "doubles as an allow-list of
   permitted callers". But the page's own resolution algorithm, step 3, says an app id that is *not*
   on the list is attributed from its header - not refused. In Phase 0 the list excludes nobody. It
   is a name map with an allow-list *ambition* (the code comments say "closed allow-list", which is
   RFC intent). Reworded throughout: "list of known clients", and a sentence saying plainly that it
   does not yet exclude anyone. This is the "design smell vs mismatch" case in miniature: the docs
   had absorbed the code's own optimistic vocabulary.

4. **The Storage API overview stated an infrastructure fact** - "in a deployment it sits on a private
   network" - the day after the decision that infrastructure facts live in preservation-ops and are
   not restated. Softened to "is designed to sit on", which is the design claim the docs can stand
   behind. (RFC-0001 s7 says "should remain reachable only from", not "is".)

5. **A forward promise on a public page.** The transitional-arrangement aside said the
   `X-Client-Identity` header "will be dropped altogether". That is RFC-0001 Phase 4, which is a plan.
   Now "is expected to be".

6. **Two findings were in the wrong bucket.** The `example.com` seed row was under "not worth an
   issue" - but it is the first thing every unattended consumer of the activity stream reads, so it
   is now #269. And `DisableAuth: "true"` in the Storage API's example settings was under "needs a
   decision" - it does not; it needs a one-character PR, and the findings index now says so.

## Judgement calls, for Tom

These are not errors. They are places where the documentation is accurate and something else should
probably happen.

- **#267 is going to become a security boundary.** Today a hand-written Import Job naming the wrong
  Archival Group is a footgun, not an escalation - any caller can already write anywhere. But
  RFC-0001 is heading for per-caller roles and per-caller buckets, and at that point
  `JobDoesNotBelongToDeposit` is checking that the *bytes* come from your workspace and not that the
  *target* is yours. Better to add the one-line comparison now. Commented on the issue.

- **The pipeline wiping `metadata/` is a design question, not a doc note.** It silently destroys any
  tool output you placed there yourself, from the workspace *and* the METS. The site carries a danger
  aside, which is the most the docs can do. The platform could instead refuse to run when
  `metadata/` holds content it did not write, which would turn a data-loss trap into a `409`. Worth
  raising against the pipeline rather than leaving as a warning readers will not see until too late.

- **The deposit IIIF token lives in a per-process `IMemoryCache`.** Under the "experimental gimmick"
  framing this is low priority, and it is behind a feature flag. But if that flag is ever turned on
  behind a multi-instance load balancer, every tokenised URL will fail on the instance that did not
  mint it, and the symptom ("session expired") will send people to the wrong place. One line in the
  deployment internals would save someone a day.

- **"Any valid token can call any operation" is stated on a public page.** It is true, RFC-0001 is
  public in the code repo, and it is not exploitable information (you still need a token that Entra
  will only issue to assigned callers). I would leave it - an integrator deserves to know - but it is
  the kind of sentence someone at Leeds may want to have chosen to publish rather than discover.

- **`browse-root.jpg` is the first screenshot a reader sees, and it is a dev instance full of
  `bm-test-*` clutter.** Honest, and not flattering. A cleaner container would make a better
  frontispiece; a judgement about how the platform wants to be seen, not a correctness issue.

## Half-finished features: how each is presented

| Feature | State | How the site treats it | Verdict |
|---|---|---|---|
| Editability judge | PR #238 open | "designed as", "not yet part of the platform", shipped rule stated separately | Right |
| `/whoami`, known clients, bucket routing | On the branch, not on `main` | Documented as current; Tom accepted ("near release") | Right, given the assumption |
| IIIF manifests | Experimental scaffolding | Caution at the top; purpose and aims separated; `paintedResources` named as an aim with nothing emitting it | Right |
| Access conditions to IIIF-CS roles | Not designed | "How that is expressed is not settled, and none of it is built" | Right |
| METS ID normalisation | Behind a flag, built for a migration tool | Flag named; "where the flag is off, the route is not there" | Right |
| Renames in Import Jobs | Accepted, never performed (#260) | Stated plainly on two pages | Right - but the docs should not have to say this for long |
| Deposit archiver / `archived` | Deployed as a Lambda the deploy job never restarts | Described as a lifecycle state; deployment caveat lives in internals | Acceptable |

The pattern that works, and the one to keep: say what the platform does *today* in the main text,
put the direction in an aside, and name the PR or issue so the claim can be dated.

## Consistency across sections

Checked by grep across all 46 pages, not by reading:

- **`metsETag`** - the rule (only `GET /deposits/{id}` populates it; null on create and in listings)
  is now stated identically on deposits, editing-mets, quickstart, recipes and the three workflow
  pages that use it. Consistent.
- **Pipeline writes the METS** - now consistent across tool-outputs, managed-mets-deposit, the
  quickstart's managed tab, recipes, and (after this review) editing-mets.
- **The Storage API and METS** - now consistent across components, storage-api/overview and the
  verification file's own claim.
- **`template` is never echoed back** - only one page shows a deposit response where a non-`None`
  template was asked for, and it carries the comment. Consistent.
- **Heading forms** - `## 📦 ArchivalGroup` on the repository page (the JSON type) and
  `## 📦 Archival Group` on the concepts page (the concept). Defensible, since one is a type name and
  one is prose, but a reader who notices will wonder. Left alone; flagging.
- **Status codes** - the second verification pass found seven wrong ones on the newer pages and all
  are fixed. I did not re-verify every code on every page; the two passes did that.

## Process observations

Worth recording because they are the kind of thing that recurs.

- The verification summary claimed two fixes that were not made (above). Verification found the
  errors; nothing verified the fixing.
- Three of the four broken sequences in the whole site were in a page written from memory in a few
  minutes (`recipes.mdx`). Already recorded as a lesson in the findings; it bears repeating because
  short snippets are what get copied.
- Forty-one commits sat unpushed for most of a day, and `git status` said nothing because the branch
  had no upstream. Tom found out by looking on GitHub. "Committed" was said many times when "pushed"
  was what mattered.
- `findings-F.md` was overwritten by accident and recovered from git. The recovery was clean, but it
  is why there are now both `findings-original-list.md` and `findings.md`.
- The `.env` for the samples was correctly kept out of git, and the security sweep found and removed
  a real account email that an agent had carried over from the old documentation into two committed
  pages. That sweep should be a fixed step before any publish, not something remembered.

## Recommendations, in order

1. Merge `docs-site`; switch Pages to "GitHub Actions". Until then the superseded banners on
   `documentation/02c-e` are only on this branch, and Leeds reading `mets-profiles` do not see them.
2. Make the `DisableAuth` example-settings fix as a PR. One character.
3. Add the `archivalGroup` comparison from #267 before the RFC-0001 roles land.
4. Decide whether the pipeline should refuse to wipe foreign `metadata/` content, or keep the warning.
5. Install `starlight-links-validator` so the link sweep is not a one-off script.
6. When any of #258-#269 closes, search the site for the note that references it; each was written
   to be removed.

## Not done in this review

I did not re-run the samples, re-verify status codes page by page, or re-read the six METS pages

sound. I read the three judgement pages in full, grepped the whole site for the contradictions the
session's own history made likely, and diffed the verification summary against the pages. That last
check is the one that found the most.
