The iiif-builder is a long-running Python service that turns preserved Archival Groups into published [IIIF](https://iiif.io/) Manifests. It is the platform's first and best example of a **consumer of the activity stream**: it is not called by anything, it holds no special position, and the platform does not know it exists. It finds out that an object has changed by reading the stream, like any other client could.

It is worth understanding for that reason even if you never touch IIIF - anything that derives something from preserved content, be it a search index, an access copy or a report, can be built the same way.

## What it does

<Steps>

1. **Read the activity stream.** Every 60 seconds by default, it asks the Preservation API's [activity stream](../../preservation-api/activity-stream) for its `last` page, walks the entries backwards until it reaches one it has already seen, and follows `prev` to earlier pages if it needs to. "Already seen" means an `endTime` at or before the latest one recorded in its own database.

2. **Decide whether this one is ours.** Archival Group paths are matched against a configured list of prefixes. Anything outside them is recorded as skipped and dropped. A single repository holds far more than the material that should become public IIIF.

3. **Load the object and its METS.** `GET` the Archival Group, then `GET` it again with `?view=mets` for the METS XML, which is parsed into the same physical structure the Preservation API works with.

4. **Ask the Leeds Identity Service who this is.** A lookup by repository URI returns the item's persistent identifier, the public IIIF Manifest URI it should be published at, and the URI of its catalogue record. Exactly one result is required: none, or more than one, is an error.

5. **Fetch descriptive metadata** from the catalogue API and turn it into the Manifest's labels, summary and metadata pairs.

6. **Build the Manifest.** Start from a boilerplate Manifest carrying the institutional `provider` block, add the descriptive metadata, then add one *painted resource* per image file found in the METS structure.

7. **PUT it to IIIF Cloud Services.** `GET` first to see whether a Manifest is already there; if so, capture its ETag and send the new one with `If-Match`, so a concurrent change is not silently overwritten.

</Steps>

Each step's outcome is written to a row in the service's own database, so a failure is recorded against the activity that caused it rather than only appearing in the logs.

## Painted resources, and why

The Manifest the iiif-builder sends has no `items`. Every image is expressed as a **painted resource**: a pairing of an asset (the file, by its S3 origin) with a `canvasPainting` giving the canvas id, its order and its label. IIIF Cloud Services generates and manages the Canvases from those.

The origin of each asset comes from the Archival Group's `origin` combined with its [storage map](../../storage-api/activity-and-content#the-storage-map), which gives the real S3 key of the file as it exists in the current version. So the image server is pointed straight at the preserved bytes; nothing is copied to build a Manifest.

Files that are not images are skipped. On an update, the builder compares each asset against the existing Manifest and marks only those whose origin has changed for reingest, so that a new version of an object does not cause every image in it to be re-derived.

<Aside type="note">
The origin lookup is why this service needs the `storageMap` on an Archival Group. It could instead
walk the Container hierarchy and read the `origin` of the Binary at each path, which gives the same
answer; the storage map is simply less code.
</Aside>

## Configuration

All configuration is environment variables, read from a `.env` file if one is present. There are no other settings.

### Activity stream

| Variable | Purpose |
|---|---|
| `PRESERVATION_ACTIVITY_STREAM` | The URI of the Preservation API's Archival Group activity stream collection. |
| `ACTIVITY_STREAM_READ_INTERVAL` | Seconds between polls. Default `60.0`. |
| `ACTIVITY_CUTOFF_DATE` | Overrides the "last seen" time from the database. An ISO 8601 timestamp, or the literal `now` to ignore everything that has already happened and start from this moment. Unset is the normal case. |
| `ARCHIVAL_GROUP_PREFIXES_TO_PROCESS` | Comma-separated repository path prefixes to process. Everything else is skipped. |
| `POSTGRES_CONNECTION` | The service's own database. |

<Aside type="caution">
`ACTIVITY_CUTOFF_DATE` is the knob to reach for when the service has fallen a long way behind, or
when a redeployment should not replay history. An unparseable value silently becomes "now"; with the
variable unset and an empty database, the service starts from a date hard-coded in `db.py`.
</Aside>

### Calling the Preservation API

| Variable | Purpose |
|---|---|
| `PRESERVATION_CLIENT_ID`, `PRESERVATION_CLIENT_SECRET`, `PRESERVATION_TENANT_ID` | The client-credentials registration. The scope and authority are derived from these. |
| `IIIF_BUILDER_IDENTITY` | The value sent as `X-Client-Identity`, and therefore the [Agent](../../preservation-api/agents) name the builder's reads are attributed to. Default `iiif-builder`. |
| `PRESERVATION_CLIENT_IDENTITY_HEADER` | The header name. Only worth changing if the API's changes. |
| `PRESERVATION_COLLECTIONS_CONTAINER_ALIASES`, `PRESERVATION_COLLECTIONS_HOST_ALIASES` | Development conveniences: rewrite the container or host in an Archival Group URI before asking the Identity Service about it, so that a dev instance can look up identifiers minted against production URIs. |

The builder uses MSAL to obtain and cache its token. It is a machine client with no user context; see [Authentication](../../preservation-api/authentication).

### Identity Service and catalogue

| Variable | Purpose |
|---|---|
| `IDENTITY_SERVICE_BASE_URL` | Base URI of the Leeds Identity Service. |
| `IDENTITY_SERVICE_API_HEADER`, `IDENTITY_SERVICE_API_KEY` | Its API key, sent as a header. |
| `CONSTRUCT_CATALOGUE_API_URI` | When set, build the catalogue URI from the PID and the prefix below instead of using the one the Identity Service returned. |
| `MVP_CATALOGUE_API_PREFIX` | The prefix used when constructing that URI. |
| `MVP_CATALOGUE_API_HEADER`, `MVP_CATALOGUE_API_KEY_VALUE` | The catalogue API's key. |

### IIIF Cloud Services

| Variable | Purpose |
|---|---|
| `IIIF_CS_PRESENTATION_HOST` | Where Manifests are PUT. |
| `IIIF_CS_CUSTOMER_ID` | The customer the Manifests belong to. |
| `IIIF_CS_ASSET_SPACE_ID` | The asset space images are registered in. |
| `IIIF_CS_BASIC_CREDENTIALS` | Basic auth credentials, sent base64-encoded. |
| `REWRITTEN_PUBLIC_IIIF_PRESENTATION_PREFIX` | The public Manifest prefix the Identity Service knows about. The builder strips it from the public URI to work out the corresponding URI inside IIIF Cloud Services, so that the Identity Service only ever has to hold the public, rewritten form. |

## Its database

One table, `archival_group_activity`, with a row per activity stream event the service has read: when the event happened, which Archival Group it was about, the PID and Manifest URIs that were resolved for it, when processing started and finished, and the error message if it did not. `max(activity_end_time)` over that table is what tells the service where it got to, so the table is the service's only state.

<Aside type="caution" title="The table is not created for you">
There is no migration step. The `CREATE TABLE` statement lives in a comment at the foot of
`src/iiif-builder/app/db.py`, and someone has to run it against a new database before the service
will do anything. Worth knowing when standing up a new environment.
</Aside>

## Building and running it

The service is a small Python 3.12 image, built and deployed by its own GitHub Actions workflow rather than with the .NET services, because it changes on a different rhythm. Locally, `docker-compose.local.yml` will bring it up alongside its database - see [Deployment](../deployment#running-locally).
