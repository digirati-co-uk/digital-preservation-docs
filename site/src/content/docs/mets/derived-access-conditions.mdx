This page describes an **optional** extension to the access metadata described on the
[descriptive metadata page](../mets-we-write-descriptive#access-restrictions). A standard instance of the
platform records two things about a resource — an access restriction and a rights statement — and
computes nothing from them. If `GET /access-conditions` on your instance returns an empty `derived` list,
nothing on this page applies to you.

An instance can configure the platform to **derive** further access conditions from those two choices:
a third `mods:accessCondition`, with a `type` of the instance's choosing, whose value is looked up from the
effective restriction and the effective rights statement. The platform computes it on every write of a
METS file and never accepts it as input. The motivating case is Leeds, whose delivery systems need an
**Access Tier** from 0 to 5 that combines the Protected Access Level of an item with its copyright status.

## How a derived value is computed

A derived value is a cell in a matrix:

- The **rows** are the restriction vocabulary's values, plus `__none__` for a resource with no effective
  restriction at all.
- The **columns** are **rights groups**. A matrix with one column per rights URI would be unmanageable,
  so the instance partitions the rights-statement vocabulary into named groups — "out of copyright",
  "in copyright but low risk", and so on.
- The **cell** is the derived value.

Both inputs are the *effective* values — what applies to the resource after inheritance — so a file that
sets only a rights statement gets a value that reflects the restriction it inherits from its folder.

## What the profile holds

The two parts of the [access condition profile](../../preservation-api/vocabularies#access-conditions)
that a standard instance leaves empty:

| Property | Description |
|---|---|
| `rightsAxis.groups` | A list of groups, each with a `key`, a `label` and `members`. Members name rights statements by their short label (`InC`, `NoC-US`, `CC-BY`...). Two reserved members: `__none__` claims a resource with no effective rights statement, and `*` claims any statement no other group names. When groups exist a user interface should offer only the grouped statements, under their group labels: a statement outside every group has no column, so it cannot be chosen. |
| `derived` | A list of derived conditions, each with the `type` written to METS, a `label`, its possible `values` in order from least to most restrictive, and a `matrix` of restriction value → group key → derived value. A row key or column key of `*` matches anything a more specific key does not. |

## Worked example: the Leeds Access Tier

Leeds chooses a **Protected Access Level** (the restriction) and a **Copyright Statement** (the rights
statement), and derives an **Access Tier**. Its profile, as `GET /access-conditions` returns it:

```json
{
  "allowMultipleRestrictions": false,
  "restrictionAxis": {
    "label": "Protected Access Level",
    "values": [
      { "value": "PA1", "label": "Level 1" },
      { "value": "PA2", "label": "Level 2" },
      { "value": "PA3", "label": "Level 3" },
      { "value": "PA4", "label": "Level 4" },
      { "value": "PA-unassessed", "label": "Unassessed" }
    ]
  },
  "rightsAxis": {
    "label": "Copyright Statement",
    "groups": [
      { "key": "public-domain", "label": "Out of copyright (public domain / CC0)",
        "members": ["NoC-US", "NoC-NC", "NoC-OKLR", "NoC-CR", "NKC", "CC0", "CC-BY", "CC-BY-SA"] },
      { "key": "low-risk", "label": "In copyright: assessed, low risk / permission given",
        "members": ["InC-EDU", "InC-NC", "CC-BY-NC", "CC-BY-ND", "CC-BY-NC-SA", "CC-BY-NC-ND"] },
      { "key": "restricted", "label": "In copyright (restrictions apply)",
        "members": ["InC", "InC-OW-EU", "InC-RUU"] },
      { "key": "unassessed", "label": "Copyright unassessed",
        "members": ["CNE", "UND", "__none__", "*"] }
    ]
  },
  "derived": [
    {
      "type": "tier",
      "label": "Access Tier",
      "values": [
        { "value": "0", "label": "Tier 0 - Open" },
        { "value": "1", "label": "Tier 1 - Open" },
        { "value": "2", "label": "Tier 2 - Restricted" },
        { "value": "3", "label": "Tier 3 - Protected" },
        { "value": "4", "label": "Tier 4 - Closed" },
        { "value": "5", "label": "Tier 5 - Unassessed" }
      ],
      "matrix": {
        "PA1":           { "public-domain": "0", "low-risk": "1", "restricted": "2", "unassessed": "2" },
        "PA2":           { "*": "3" },
        "PA3":           { "*": "3" },
        "PA4":           { "*": "4" },
        "PA-unassessed": { "*": "5" },
        "__none__":      { "*": "5" },
        "*":             { "*": "5" }
      }
    }
  ]
}
```

Reading the matrix:

| Effective restriction | Effective rights statement | Group | Tier |
|---|---|---|---|
| `PA1` | `NoC-US` | public-domain | 0 |
| `PA1` | `InC-EDU` | low-risk | 1 |
| `PA1` | `InC` | restricted | 2 |
| `PA1` | none — nothing set, nothing inherited | unassessed, via `__none__` | 2 |
| `PA2` | anything | — (`*`) | 3 |
| `PA4` | anything | — | 4 |
| none | anything | the `__none__` row | 5 |
| any value outside the vocabulary (legacy content) | anything | the `*` row | 5 |

This JSON is also, key for key, the Preservation API's `AccessConditionProfile` configuration section
— the API returns what it was configured with. How and where to configure it, and what to think about
when changing a profile that is already in use, is in the code repository's
[access condition profile](https://github.com/digirati-co-uk/digital-preservation/blob/main/docs/internals/access-condition-profile.md)
notes for operators.
</Aside>

## What it produces

**In METS**, a third `accessCondition` beside the two chosen ones, on every div (physical or logical) that
carries an explicit choice of its own, and on every file whose effective inputs come partly from its
logical range:

```xml
<mods:accessCondition type="restriction on access" xlink:type="simple">PA2</mods:accessCondition>
<mods:accessCondition type="use and reproduction" xlink:type="simple">http://rightsstatements.org/vocab/InC/1.0/</mods:accessCondition>
<mods:accessCondition type="tier" xlink:type="simple">3</mods:accessCondition>
```

Every write recomputes every derived value in the document, so a stale value cannot survive a save, and
the writer touches only the types the instance currently derives. The full rules are on the
[writer page](../mets-we-write-descriptive#derived-access-conditions); how the values are read back and
inherited is on the [reader page](../mets-we-read#effective-metadata-inheritance).

**On the API**, two read-only properties on every file and folder in a Deposit's
[file listing](../../preservation-api/deposit-files): `derivedAccessConditions` (what the resource carries
itself) and `effectiveDerivedAccessConditions` (what applies after inheritance), each a map from `type`
to value. Logical Ranges carry the same. There is no way to set them.

**In the Preservation UI**, the derived value appears in the file table beside access and rights, and the
metadata dialogue recomputes it live as you change the two choices, so you see the consequence of a
decision before saving. See [Working with deposits](../../ui/deposits#access-conditions-rights-and-record-identifiers).

## Constraints

- A derived value is a single matrix cell, so an instance that derives anything must allow only one
  restriction per resource (`allowMultipleRestrictions` false). Legacy content carrying several uses the
  most restrictive of them, by the order of the restriction vocabulary, for the lookup.
- The profile is validated when the Preservation API starts, and a matrix that names an unknown row,
  column or value, or that leaves any restriction without a value for any group, stops the service. A
  client can therefore trust that every cell names one of the declared `values`, and that every
  combination of a vocabulary value (or none) and a group resolves to something.
- The grouping of rights statements into columns is the instance's inference, not a property of the
  statements: a URI says nothing about risk. The Leeds grouping above is the one assumed on
  [issue #433](https://github.com/digirati-co-uk/digital-preservation/issues/433), where it is set out
  statement by statement for Leeds to confirm.
- The platform does not know what a derived value *means*. Mapping a tier to IIIF authorisation roles,
  or to anything else, is the delivery system's business.
