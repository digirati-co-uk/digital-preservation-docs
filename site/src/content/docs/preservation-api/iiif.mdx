A preserved object and a [IIIF](https://iiif.io/) Manifest describe overlapping things: an ordered set of files, some of which are images or audio-visual, arranged into a structure that means something to a reader. The Preservation API can project either an [Archival Group](../repository#-archivalgroup) or a [Deposit](../deposits) as a [IIIF Presentation 3](https://iiif.io/api/presentation/3.0/) Manifest.

<Aside type="caution" title="Read this before using these manifests">
This is **new**. The design is on [#261](https://github.com/digirati-co-uk/digital-preservation/issues/261).
Two parts of the IIIF Cloud Services manifest depend on changes to IIIF Cloud Services that are not
yet released: see [Submitting to IIIF Cloud Services](#submitting-to-iiif-cloud-services).
</Aside>

## What this is for

These manifests are **not** IIIF representations of your objects that you can put on the web. They are not intended to be viewed by the public, served from a public address, or treated as the institution's published IIIF.

What they are for is **scaffolding a downstream IIIF builder**. The platform already knows things such a builder would otherwise have to work out for itself from the METS: which files are the object's content and which are derivatives of other files, what order they go in, their dimensions and durations, how the logical structure nests, and what access conditions apply to each part. Emitting that as a Manifest — canvases, ranges, annotations for `smLink`-ed files — means a builder can start from a structure rather than from a pile of XML.

The expected arrangement is:

<Steps>

1. The Preservation API produces the scaffolding: structure, relationships, extents, access conditions, and references to the preserved files.

2. A downstream builder decorates it with descriptive metadata from the catalogue and **registers the assets with a IIIF delivery platform** — for Leeds, Digirati's IIIF Cloud Services — which is what actually serves image tiles, audio and video to the public.

3. That platform publishes the public Manifest.

</Steps>

## Two kinds of manifest

| | Vanilla | IIIF Cloud Services |
|---|---|---|
| For | Deposits and Archival Groups | Archival Groups only |
| Archival Group | `GET /repository/{path}?view=iiif` | `GET /repository/{path}?view=iiif-cs` |
| Deposit | `GET /deposits/{id}/iiif`, which redirects to a tokenised URL | — |
| Canvases | Every canvas is a placeholder | No painting: IIIF Cloud Services paints them |
| Files | An Archival Group canvas links to its Binary as `rendering`; a Deposit canvas links to nothing | Each canvas's file is an asset in `paintedResources`, with its location in preservation storage |

The **vanilla** manifest is plain IIIF, which you can open in any viewer to see the shape of an object: its files in order, their structure, their metadata and their access conditions.

The **IIIF Cloud Services** manifest is what a builder submits, once decorated, to IIIF Cloud Services. It is only for Archival Groups because it names where each file's content is in preservation storage, which a delivery platform with access to that storage ingests from. It is JSON for a program, not something to open in a viewer.

Only the current version of an Archival Group is projected.

## What ends up in a manifest

Both kinds are built from the [METS](../../mets/overview) file: its physical structure supplies the canvases, its logical structMaps and folders the ranges, its links the annotations.

### Canvases

* **One per file below `objects/`**, in METS order. A file is skipped if the platform does not know its media type, or if it is the *target* of a link from another file — a transcript, a caption file or OCR, which belongs with the file it describes rather than on a canvas of its own.
* **The canvas `id`** ends with an identifier made from the file's full path under `/repository` — the same identifier a builder is given as the asset's suggested `id`, so the two line up. It is the path encoded the way METS IDs are (`/` becomes `_x002F_`, and so on), made ASCII by folding accents and escaping anything else, and with a hash on the end whenever folding lost something or the path is too long. So `library/ms-342/objects/page-001.tif` gives `library_x002F_ms-342_x002F_objects_x002F_page-001.tif`. Treat it as opaque: don't read a path back out of one. A renamed file gets a new identifier; a changed file keeps its identifier.
* **`metadata`** describes the file: its original name and path, size, format name, PRONOM key, media type, SHA-256 digest, the result and date of its virus check, and its extents. Every label starts with `Preservation: `, so a builder adding its own metadata from the catalogue can find and remove ours. Record identifiers recorded for the file in METS appear here too.
* **`accessConditions`** and **`rights`** — see [Access conditions](#access-conditions).

In the vanilla manifest:

* **Every canvas is a placeholder**, whatever kind of file it is for. The platform holds only the originals — a master TIFF, an archival video — and nothing web-friendly is made from them until a builder registers them with a delivery platform. Each canvas has `behavior: ["placeholder"]` and an image painted over the whole canvas that shows the file's media type and PRONOM key.
* **A canvas keeps the file's own size.** Width, height and duration come from the extents recorded in METS, which the [pipeline](../tool-outputs-and-pipelines) puts there, so a Range's `#xywh` or `#t` fragment means the same on the canvas as in the file. A file with no recorded width and height gets a 1000 × 800 canvas.
* **An Archival Group canvas links to its Binary** as `rendering`, with `behavior: ["original"]`: the Binary's `/repository/...` URI, which returns a JSON description, not the file — the Preservation API does not serve file content (see [Fetching file content](../repository#fetching-file-content)). A **Deposit canvas links to nothing**: a deposit's files are reached through the [Preservation UI](../../ui/deposits) and the API, not from its manifest.

In the IIIF Cloud Services manifest, a canvas has no painting, no extents and no `rendering`: IIIF Cloud Services paints it from the asset, takes the extents from the asset, and the builder chooses how the asset is delivered.

### The placeholder images

```
GET /placeholders/canvas/1000x800/fmt/353/image/tiff
GET /placeholders/thumb/image
```

The canvas image shows the media type and the PRONOM key (or "Unknown format", as `fmt/0`). It has the canvas's aspect ratio, within limits: its long side is 1000 pixels, the ratio is held between 1:4 and 4:1, and both sides are multiples of 50. That leaves room for a thumbnail made later to be painted in its place without the canvas changing. The thumbnail is one of four, `image`, `video`, `audio` or `file`.

These routes are **anonymous**, because a viewer has no way to send a token, and they can be, because an image is chosen by a file's format and never by the file: it says nothing about what is preserved. Any size, key or media type the projection would not use is a `404`. The images are set in [Public Sans](https://github.com/uswds/public-sans), under the SIL Open Font Licence.

### Linked files

A file that another file [links to](../deposit-files) — a transcript, closed captions, OCR — gets no canvas. In the vanilla manifest it becomes a supplementing annotation on the canvas of the file it belongs to, with a `provides` value from the link's role (`transcript`, `closedCaptions` and so on). In an Archival Group manifest the annotation's body is the Binary's URI; in a Deposit manifest it is an identifier, not a link. So a viewer showing a Deposit finds nothing at a caption file's address: the Deposit manifest is shaped like the one the preserved object will have, not made to play.

In the IIIF Cloud Services manifest it becomes an **adjunct** of the main file's asset, so IIIF Cloud Services ingests and serves it and makes the annotation itself (`iiifLink: "inlineAnnotation"`, `motivation: "supplementing"`, and `provides`).

<Aside type="note">
`provides` comes from IIIF Presentation 4, and is included now because it is so useful. IIIF Cloud
Services keeps it on the adjunct, but will only write it into its own manifests once it supports
Presentation 4.
</Aside>

### Ranges

* **Logical structure**: one top-level Range per logical structMap, nested as deeply as the METS nests them. A Range's items are canvases, with a [media fragment](https://www.w3.org/TR/media-frags/) where the METS file pointer gives an area (`#t=10,20`, `#xywh=0,0,500,400`). Each Range carries its structure type and name, its record identifiers, and its access conditions.
* **Folders**: when some file below `objects/` sits in a subfolder, the folder tree becomes one more top-level Range, after the logical ones, with each folder's files in METS order and then its subfolders. It records the original arrangement, and it is there even when there are logical structMaps; a consumer that doesn't want it can drop it. A flat `objects/` has no folder Range — including the common case of images with their OCR files beside them — and nor does a folder whose files are all linked files.

### The manifest

`label` is the Archival Group's name, or the Deposit's title. `seeAlso` points at the METS and at the Archival Group (or Deposit) itself. The manifest carries the access conditions and record identifiers of the object as a whole: those of the `objects/` folder, which is where the platform records them. A Deposit manifest's `metadata` also summarises the deposit: its status, its Archival Group, who created, preserved and exported it and when, and how many files the METS describes.

## Access conditions

Every canvas, every Range and the manifest itself carry the access conditions that apply to them, **as they are after inheritance** — the same values the [Preservation UI](../../ui/deposits) shows for each file:

```json
"accessConditions": [
  { "type": "restriction on access", "value": "PA3" },
  { "type": "use and reproduction", "value": "http://rightsstatements.org/vocab/InC/1.0/" },
  { "type": "copyright statement", "value": "inc-low-risk" },
  { "type": "tier", "value": "3", "derived": true }
]
```

Each entry is a `mods:accessCondition` from the METS: its `@type` and its value. Conditions an installation computes from the others — for Leeds, the Access Tier, type `tier` — are marked `derived`. The values are the profile's own codes (`PA3`, `inc-low-risk`, `3`); `GET /access-conditions` gives their labels. The effective `use and reproduction` statement is also given as IIIF `rights`.

The point is that a builder registering assets doesn't need its own copy of the platform's inheritance rules. What the archivist saw on the deposit is what the builder turns into roles and other access configuration on the delivery platform. The shape is the same whatever an installation's [access condition profile](../vocabularies) is; the types and values are its own.

`accessConditions` (and, in the IIIF Cloud Services manifest, `formerAssets`) are defined in a JSON-LD [context document](https://digirati-co-uk.github.io/digital-preservation-docs/ns/iiif/context.json), declared once at the head of the manifest as a scoped term, before the Presentation context:

```json
"@context": [
  {
    "accessConditions": {
      "@id": "https://digirati-co-uk.github.io/digital-preservation-docs/ns/iiif#accessConditions",
      "@context": "https://digirati-co-uk.github.io/digital-preservation-docs/ns/iiif/context.json"
    }
  },
  "http://iiif.io/api/presentation/3/context.json"
]
```

A JSON consumer can ignore all of that and key on the property names. The context's address is configuration (`Iiif:ExtensionContext`), because this site's address may change.

## An Archival Group as a Manifest

```
GET /repository/library/manuscripts/ms-342?view=iiif
GET /repository/library/manuscripts/ms-342?view=iiif-cs
```

An Archival Group links to both, as its `iiif` and `iiifCs` properties; a Deposit links to its own as `iiif`. For the whole path from a preserved object to IIIF published by IIIF Cloud Services, see [IIIF from preserved objects](../../workflows/iiif-cloud-services).

The path must be an Archival Group: a Container or a Binary gives `404`, as does an Archival Group with no METS file in it. A `version` parameter is a `400`. The manifest's `id` is the request URI. These need the same bearer token as the rest of the API.

### Submitting to IIIF Cloud Services

The `?view=iiif-cs` manifest adds what IIIF Cloud Services needs to register and paint each file:

```json
"paintedResources": [
  {
    "canvasPainting": { "canvasId": "library_x002F_ms-342_x002F_objects_x002F_page-001.tif", "canvasOrder": 0 },
    "asset": {
      "id": "library_x002F_ms-342_x002F_objects_x002F_page-001.tif",
      "mediaType": "image/tiff",
      "origin": "s3://preservation-bucket/…/v3/content/objects/page-001.tif"
    }
  }
]
```

* **`canvasId`** is the canvas's `id`, which in this manifest is the short identifier, and **`canvasOrder`** is the canvas's place in `items`.
* **`asset.origin`** is where the file's content is in the preservation store's OCFL layout. That location never changes: a new version of the file is a new location, so a changed `origin` means changed content. A delivery platform integrated with the platform has read access to the store for this.
* **`asset.id`** is a suggestion — the same identifier as the canvas. `space`, delivery channels and roles are left to the builder.

It also has **`formerAssets`**: every file below `objects/` that an earlier version of the Archival Group had and this one doesn't — removed, or renamed from that path — with the last version it was in and its last `origin`:

```json
"formerAssets": [
  { "id": "library_x002F_ms-342_x002F_objects_x002F_page-099.tif", "lastVersion": "v2", "origin": "s3://…/v1/content/objects/page-099.tif" }
]
```

It lists them all, every time, so a builder doesn't need to know which versions it has processed: it can delete whichever of these it registered. One case is not listed: a file that is still there but has become the *target* of a link, so it is now an adjunct rather than an asset.

Two parts of this rely on changes to IIIF Cloud Services that are not yet released:

* [dlcs/iiif-presentation#726](https://github.com/dlcs/iiif-presentation/issues/726): IIIF Cloud Services rewrites a matched canvas's `id` into its own form. Until it rewrites references to that canvas in `structures` too, the Ranges in a submitted manifest point at ids that no longer exist.
* [dlcs/iiif-presentation#727](https://github.com/dlcs/iiif-presentation/issues/727): until a changed `origin` reaches the asset, re-submitting the manifest after a file has changed does not re-ingest it unless the builder adds `"reingest": true` to that painted resource.

## A Deposit as a Manifest

A Deposit's working area is private, so the deposit manifest is served from a short-lived, unguessable URL.

```
GET /deposits/e56fb7yg/iiif
```

This is an authenticated request, and its answer is a redirect:

```
HTTP/1.1 302 Found
Location: /deposits/e56fb7yg/iiif-token/9f3c1a4b7d2e8065c4a1b9f70d3e2a18
```

Follow it, and you get the manifest:

```
GET /deposits/e56fb7yg/iiif-token/9f3c1a4b7d2e8065c4a1b9f70d3e2a18
```

The tokenised URL needs no `Authorization` header, so you can hand it to a viewer running in a browser, which has no way to obtain your token. The manifest links to none of the deposit's files, so the token opens the manifest and nothing else. Canvas ids use the path of the Archival Group the deposit will become, when it names one, so they match what the preserved object's manifest will say.

<Aside type="caution">
The token is the *only* protection on the manifest, which describes every file in the deposit. Treat it like a password: do not put it in a bug report, a shared document or a URL you paste into a chat. It lasts eight hours from last use, and at most a week however often it is used, and it does not survive a restart of the API. Fetch `/deposits/{id}/iiif` again to get a fresh one.
</Aside>

The tokenised routes are controlled by the `EnableIiifMediaEndpoints` feature flag, and are off unless an instance has turned them on. When it is off, `GET /deposits/{id}/iiif` answers `404 Not Found` directly, without redirecting and without minting a token, and so does the tokenised route. (The name is historical: the media routes it once also controlled have been removed.)
