The Preservation API is the application-facing API of the platform: it is what the Preservation UI,
Goobi, the iiif-builder and most scripts talk to. It is JSON over HTTP. This page covers the
conventions that every endpoint shares; the rest of the section goes through the endpoints by topic.

## Hosts and roots

Examples throughout use `https://preservation-api.example` as the API host. Your platform instance
has its own hostname; nothing else changes.

There is no API functionality at the root URL itself (`GET /` returns a short plain-text greeting).
Resources live under top-level paths such as `/repository`, `/deposits`, `/agents` and `/whoami`.
Every resource the API returns identifies itself with an `id` that is its own fully qualified URL at
this host, and refers to other resources by their URLs, so you can navigate by following `id`
values rather than constructing paths.

The Preservation API sits on top of the [Storage API](../../storage-api/overview). Most callers never
see the Storage API; where the Preservation API passes a Storage API concept through (browsing the
repository, for instance) it rewrites the URIs so that they point at the Preservation API host.

## JSON conventions

- Property names are camelCase.
- `id` is a URI: the resource's own location in the API.
- `type` is a string naming the resource type: `Container`, `Binary`, `ArchivalGroup`, `Deposit`,
  `ImportJob`, `ImportJobResult`, and so on. The repository root has the special type
  `RepositoryRoot`.
- Dates are ISO 8601 strings in UTC, for example `2024-03-14T14:58:46.102335Z`.
- References to other resources (`partOf`, `createdBy`, `deposit`, `archivalGroup`...) are URIs.
- Properties with no value are generally omitted from the JSON rather than written as `null`.
- Request bodies are `application/json`; send `Content-Type: application/json` and
  `Accept: application/json`.

## Common metadata

Every resource shares this set of properties:

```jsonc
{
  "id": "https://preservation-api.example/...",
  "type": "Container",
  "created": "2024-03-14T14:58:46.102335Z",
  "createdBy": "https://preservation-api.example/agents/goobi",
  "lastModified": "2024-03-28T12:00:00.000000Z",
  "lastModifiedBy": "https://preservation-api.example/agents/jane.smith@example.org"
  // ... type-specific properties
}
```

| Property | Description |
| --- | --- |
| `id` | URI of the resource in the API. Its path may only contain characters from the permitted set (below). |
| `type` | The resource type. |
| `created` | When the resource was created _within the platform_ (not the original creation date of a file). |
| `createdBy` | The [agent](../agents) that created it: a URI of the form `https://preservation-api.example/agents/<name>`. |
| `lastModified` | When the resource was last modified within the platform. |
| `lastModifiedBy` | The agent that last modified it. |

Resources that represent preserved (or to-be-preserved) files and folders - Containers, Binaries and
Archival Groups - add `name`, an optional `otherNames` list, `partOf` and `origin`; see
[Repository](../repository). `ImportJob` and `ImportJobResult` carry `created` and `createdBy` but
not `lastModified`/`lastModifiedBy`, because they are never modified.

## Permitted characters in ids

The path of a repository `id` is made of slugs (path segments). Each slug may contain only:

- lower-case letters `a-z`, upper-case letters `A-Z`, digits `0-9`
- `(`, `)`, `-`, `_`, `.` and `%`

A slug must be between 1 and 2000 characters long, may not contain spaces, and may not be the word
`repository`. The API enforces this when you create a Container with PUT, when a Deposit names the
Archival Group it targets, and when an Archival Group is created by an Import Job; a slug that
breaks the rule is rejected with `400 Bad Request` and a message listing the offending characters.

Original names are not lost by this restriction. Containers and Binaries have a separate `name`
property that may contain any UTF-8 text, so a file called `Teto in tree.png` can be preserved as a
Binary whose `id` ends in `Teto_in_tree.png` (or anything else you choose) and whose `name` is the
original.

## Errors

When a request fails, the response body is an RFC 7807 problem details object:

```
GET /repository/no/such/container
```

```json
{
  "title": "Status 404",
  "status": 404,
  "detail": "..."
}
```

The status codes you will meet:

| Status | Meaning |
| --- | --- |
| `400` | Bad request - an invalid slug, a query parameter combination the endpoint does not support, a body that fails validation. |
| `401` | No valid bearer token, or no identity could be resolved for the caller. See [Authentication](../authentication). |
| `404` | Nothing at this path. |
| `409` | Conflict - something already exists at the path, an ancestor is not a Container, an active Deposit already targets the Archival Group. |
| `410` | Gone - a _tombstone_: a resource used to exist here and was deleted without being purged. |
| `412` | Precondition failed - an `If-Match` ETag did not match (see [Editing METS](../editing-mets)). |
| `422` | Unprocessable - the request was well-formed but cannot be carried out. |
| `500` | An unexpected error. |

Separately, resources that report on a long-running job (`ImportJobResult`, the pipeline's
`ProcessPipelineResult`) have an `errors` property listing error objects:

| Property | Description |
| --- | --- |
| `id` | The URI of this error. Not always present, if there is nothing sensible to reference. |
| `message` | The error message. Always present. |

## Check that you are connected

`GET /whoami` returns the identity the API has resolved for the caller, and is the quickest way to
confirm that your token is accepted and that your actions will be attributed as you expect:

```
GET /whoami
```

```json
{
  "name": "goobi",
  "source": "token",
  "appId": "5f0c1a2e-0000-0000-0000-000000000000",
  "depositBucket": "working-bucket"
}
```

| Property | Description |
| --- | --- |
| `name` | The name your actions are attributed to - the last path segment of your [agent URI](../agents). |
| `source` | How the name was resolved: `user` (a signed-in person), `token` (a machine client known to the platform by its app id), `header-fallback` (taken from your `X-Client-Identity` header) or `unknown`. |
| `appId` | The application id (`azp`/`appid` claim) from your token, when present. |
| `depositBucket` | The S3 bucket in which Deposits you create will be given their working area. |

[Authentication](../authentication) explains where each `source` comes from.
