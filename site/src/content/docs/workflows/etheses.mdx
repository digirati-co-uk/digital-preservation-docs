Use case: a script deposits theses from a repository such as White Rose. A thesis might be a single document. It might be many files in folders, especially when research data comes with it. Either way there is also a *sidecar* file of metadata about it. The script should not have to write any XML.

This is the [managed METS deposit](../managed-mets-deposit) applied to one kind of object. The platform writes the METS; the script makes API calls and uploads files. That page explains each step in more detail. This one shows the two things the script does: save a new thesis, and update one.

## What a thesis looks like

Theses live under an `etheses` Container. Each is an Archival Group, with its files under `objects/`, in whatever folders the material calls for:

```
etheses/
   my-thesis/
      objects/
         thesis.pdf
         thesis-metadata.json
         appendices/
            interview-schedule.txt
         data/
            readme.txt
            survey/
               codebook.txt
               responses.csv
      metadata/
      mets.xml
```

The sidecar sits beside the thesis because it is part of the object, not something derived from the files. In `objects/` it is listed in the METS, scanned and identified like any other file, and can be replaced like any other file.

<Aside type="note">
The sidecar's name and format here are placeholders, to be settled with Leeds.
</Aside>

## Saving a new thesis

<Steps>

1. ### Create a Deposit from the `RootLevel` template

   ```
   POST /deposits
   ```

   ```json
   {
     "type": "Deposit",
     "template": "RootLevel",
     "archivalGroup": "https://preservation-api.example/repository/etheses/my-thesis",
     "archivalGroupName": "On the preservation of theses",
     "submissionText": "Deposited by the e-theses script"
   }
   ```

   The Deposit's `files` property is the S3 location of its workspace, which already holds `objects/`, `metadata/` and a `mets.xml`.

2. ### Upload the thesis files and the sidecar

   Into `objects/`, with the S3 API, keeping the folders. Nothing has to be done to make a folder: uploading `objects/data/survey/responses.csv` is enough. No checksums are needed: the pipeline produces them.

   Set each file's content type as you upload it, and take care that it is right. The pipeline works out each file's type for itself, and a file whose two content types disagree stops the diff in step 5. A CSV file uploaded from Windows is a common case: Windows calls it `application/vnd.ms-excel`, and the pipeline calls it `text/csv`.

3. ### Run the pipeline, and wait for it

   ```
   POST /deposits/e56fb7yg/pipeline
   ```

   Then poll `GET /deposits/e56fb7yg/pipelinerunjobs` until the newest job's `status` is `completed`. The pipeline identifies each file's format, scans it for viruses, and adds every file under `objects/` to the METS with what it found.

4. ### Make sure the METS describes everything

   ```
   POST /deposits/e56fb7yg/mets
   If-Match: "bfc13a64729c4290ef5b2c2730249c88ca92d82d"
   ```

   The body is the list of every file under `objects/` and `metadata/`, taken from `GET /deposits/e56fb7yg/filesystem`. List files, not folders: a file's folders are added for it. The `If-Match` is the Deposit's `metsETag`; fetch the Deposit again to get it, because the pipeline has changed the METS. Entries already present are updated, so this is safe to call after the pipeline.

5. ### Preserve it, or leave it for a person

   The script can do either.

   **The script preserves.** Get the diff, check it, run it, and poll the result until it is `completed`:

   ```
   GET /deposits/e56fb7yg/importjobs/diff
   POST /deposits/e56fb7yg/importjobs
   ```

   The thesis is now version `v1`.

   **A person preserves.** The script stops after step 4. The Deposit is left unlocked, with status `new`, and a member of staff opens it in the UI, checks it, and preserves it there.

</Steps>

## Updating a thesis

To correct the metadata, replace the sidecar in a new version.

<Steps>

1. ### Export the thesis into a new Deposit

   ```
   POST /deposits/export
   ```

   ```json
   {
     "type": "Deposit",
     "archivalGroup": "https://preservation-api.example/repository/etheses/my-thesis"
   }
   ```

   Poll the Deposit until its `status` is `new`. Its workspace then holds every file of the thesis.

2. ### Replace the sidecar

   Upload the new sidecar to the same path under `objects/`.

3. ### Pipeline, METS, preserve

   Steps 3 to 5 of saving, unchanged.

</Steps>

The diff for this update patches the sidecar, the METS, and several of the pipeline's own output files under `metadata/`, which are rewritten on every run. The thesis and its other files are not touched, and nothing is deleted.

<Aside type="note" title="Why export, when only one file is changing?">
A Deposit can be made against an existing object [without exporting it](../update-without-export), which copies only the METS. But the pipeline writes its results for whatever is in the workspace. Run over a workspace that held only the new sidecar, its output would no longer cover the rest of the thesis. Exporting the whole object keeps the pipeline's output complete. For most theses that costs little; for one with a lot of research data, the export and the pipeline both take longer.
</Aside>

## Setting access conditions

A thesis may be embargoed, or its research data may need to be more restricted than the thesis itself. Either the script says so, or a person does.

### The script sets them

After step 4 of saving, when the METS describes every file, and before preserving:

```
POST /deposits/e56fb7yg/mets/access
If-Match: "bfc13a64729c4290ef5b2c2730249c88ca92d82d"
```

```json
{
  "path": "objects",
  "accessRestrictions": ["Restricted"],
  "rightsStatement": "http://rightsstatements.org/vocab/InC/1.0/"
}
```

`204 No Content` on success. Each call sets one file or folder, and everything beneath a folder inherits from it. So the whole thesis is one call on `objects`, and a folder or file that differs is a second call:

```json
{
  "path": "objects/data",
  "accessRestrictions": ["Closed"]
}
```

* A property you leave out is left as it is. Above, `objects/data` gets its own restriction and goes on inheriting the rights statement.
* A property sent as `null` (or an empty `accessRestrictions`) is cleared, so that the file or folder inherits again.
* The values come from the installation's own vocabulary: `GET /access-conditions` lists them. A value that isn't in it is refused with a `400` that names the choices.
* The `If-Match` is the Deposit's `metsETag`. Every call changes it, so fetch the Deposit again before the next.
* The same call can also record a file's `extent` — its `duration` in seconds, or `pixelWidth` and `pixelHeight` — for an audio, video or image file the pipeline couldn't measure. A thesis rarely needs it; see [extents entered by hand](../../mets/mets-we-write-descriptive#extents-entered-by-hand).

<Aside type="note" title="Statements instead of rights statements">
Some installations, Leeds among them, don't choose a rights statement directly. They choose one of their own statements, and the platform works out the rights statement from it. There, send `accessStatement` with one of the values `GET /access-conditions` lists under `statements`, and leave `rightsStatement` out.
</Aside>

### A person sets them

The script doesn't have to. It can create the Deposit, upload the files and run the pipeline, and stop there, as in "A person preserves" above. A member of staff then opens the Deposit in the UI, sets the access conditions on the files and folders that need them, and preserves it.
